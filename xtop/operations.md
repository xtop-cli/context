# Kernel operations

## Prerequisites

- Rust toolchain 1.87 or newer.
- `git`.
- A C toolchain is not required by the Rust code itself, but platform
  crates and the installer may expect standard build tools.

## Build and run

```
cd ~/repos/xtop-cli/xtop
cargo build
cargo run
cargo run --release
```

Default build features include the samurai plugin and the MCP extension.

```
# Pure core, no optional ecosystem pieces
cargo build --no-default-features

# Runtime widget hosts
cargo build --features plugin-wasm,plugin-external

# Everything
cargo build --all-features
```

## Local CI

```
cd ~/repos/xtop-cli/xtop
./scripts/ci.sh
./scripts/ci.sh fmt
./scripts/ci.sh clippy
./scripts/ci.sh check
./scripts/ci.sh test
./scripts/ci.sh no-default
```

Stages:

- `fmt`: format check;
- `clippy`: all targets, warnings denied;
- `check`;
- `test`;
- `no-default`: check without default features.

GitHub CI is being introduced gradually. Two workflows exist:
`.github/workflows/roadmap-sync.yml` (issue synchronization) and
`.github/workflows/release.yml` (tag-triggered release binaries). Local CI
remains the gate for day-to-day changes; do not add a new workflow without
an explicit decision.

## Structural audit

```
cd ~/repos/xtop-cli/xtop
./scripts/audit.sh
```

Fails on:

- `cfg(target_os)` outside `platform/` trees;
- files above 600 lines;
- TODO/FIXME/XXX/HACK markers;
- more than 30 wildcard re-exports;
- more than 2400 lines per top-level area;
- the dead pre-monocrate plugin tree;
- a missing theme seed or a seed count other than 12.

## Install and uninstall

Linux installer:

```
./install.sh
./install.sh --check-deps
./install.sh --install-deps
./install.sh --with-runtime-widgets
./install.sh --uninstall
./install.sh --help
```

Behavior:

- detects the distribution and package manager;
- installs build dependencies when possible;
- installs Rust through rustup when missing;
- clones the repository when not run from the project directory;
- builds in release mode;
- installs the binary to `/usr/local/bin`.

Supported distributions: Arch, Debian/Ubuntu, Fedora/RHEL, openSUSE, Alpine.

Windows:

```
.\install.ps1
.\install.ps1 -RuntimeWidgets
```

Uninstallers remove the binary only; the user configuration is preserved.

## AUR packaging

The `xtop-git` AUR package tracks the repository HEAD.

- `PKGBUILD` at the repository root is the source for the AUR repository.
- `pkgver` is generated by the `pkgver()` function from commit count and
  short hash.
- `url` and `source` point at `https://github.com/xtop-cli/xtop`.
- `depends=('gcc-libs')`, `makedepends=('git' 'cargo')`.
- The build fetches Rust dependencies with `cargo fetch --locked` and builds
  with `cargo build --frozen --release --all-features`.

Refreshing the AUR package:

1. Update `pkgver` to the current `r<commits>.<hash>`.
2. Regenerate `.SRCINFO`.
3. Run `makepkg -f` to verify the build and package contents.
4. Commit with `upgpkg: xtop-git <version>-<rel>`.
5. Push to the AUR repository.

A `-git` package does not require an upstream tag. Do not move `xtop-git` to
a release tarball; use a separate `xtop-bin` or release package instead.

## Roadmap synchronization

`ROADMAP.md` is synchronized with GitHub issues by
`.github/workflows/roadmap-sync.yml`.

- It runs when `ROADMAP.md` changes on `main`.
- The script is `.github/scripts/sync_roadmap.py`.
- Checkboxes reference issue numbers.
- Auto-commits contain `[roadmap-sync]` and are skipped to avoid loops.

## Release workflow (tag-triggered)

`.github/workflows/release.yml` runs on `v*` tags.

Jobs:

1. `gate` - full-history checkout; verifies the tag commit is an ancestor of
   `origin/main`, verifies the tag version matches `Cargo.toml`, runs
   `cargo test --locked` and `cargo check --locked --no-default-features`.
2. `build` - builds `--release --locked --all-features` for six targets:
   `x86_64-unknown-linux-gnu`, `aarch64-unknown-linux-gnu`,
   `x86_64-unknown-linux-musl`, `x86_64-apple-darwin`,
   `aarch64-apple-darwin` and `x86_64-pc-windows-msvc`.
3. `checksums` - validates each archive contains `xtop`/`xtop.exe` and
   writes `SHA256SUMS`.
4. `sign` - keyless cosign signature of `SHA256SUMS` plus build provenance
   attestations.
5. `release` - re-verifies signature and checksums, then publishes the
   GitHub Release with the archives, `SHA256SUMS` and
   `SHA256SUMS.bundle`.

Assets are named `xtop-<version>-<target>.tar.gz` (Unix) or `.zip`
(Windows) and contain the binary plus `LICENSE`, `README.md` and
`CHANGELOG.md`.

The tag must be created from a commit merged into `main`:

```
git checkout main && git pull --ff-only
git tag -a v0.1.0 -m "xtop v0.1.0"
git push origin v0.1.0
```

The `release` job references the `release` environment; protection rules
(required reviewers) are configured in repository settings, not in YAML.

## Release checklist

1. Confirm `scripts/ci.sh` passes on all default stages.
2. Confirm `scripts/audit.sh` passes. It currently fails because the
   `providers` area exceeds the 2400-line budget; resolve before tagging.
3. Confirm a `--no-default-features` build passes.
4. Confirm the installers still build.
5. Confirm the AUR package builds at the new HEAD.
6. Sync docs into the website and rebuild.
7. Update this context repository.
8. Record any policy change (versions, tags, publications) explicitly.
9. Push the tag and confirm the `release.yml` run succeeds.

## Troubleshooting

- A layout renders blank areas: a widget id does not resolve. Check the
  stderr warning and the compiled features.
- `xtop plugin install` fails at `cargo check`: the plugin is incompatible
  with the current contracts or toolchain.
- Theme looks wrong: verify the palette roles and let the normalizer run.
- Runtime widgets are not loaded: the feature is not compiled in, or the
  discovery directory is wrong.
- MCP tools fail: the samurai feature must be enabled along with the MCP
  extension.
